# Learning guide: the ideas behind this project

Read this alongside the code. Each section explains one idea, points to where it lives in the
repo, and ends with the interview question it answers.

---

## 1. The Medallion architecture (bronze → silver → gold)

Three layers, each with one job:

- **Bronze**: an exact, append-only copy of what the source sent, plus *when* it arrived. Never
  cleaned, never deleted. If you find a bug in your cleaning logic in six months, you rebuild
  silver from bronze instead of asking the source team to resend data.
- **Silver**: cleaned, typed, de-duplicated. Exactly one current row per business key. This is
  the layer other teams can trust.
- **Gold**: shaped for a use case. Here that's a star schema for analytics.

Code: `lakehouse/jobs/bronze.py`, `silver.py`, `gold.py`.

> **Q: Why not clean the data while loading it?**
> Because then the raw data is gone. Bronze lets you replay history, audit what the source
> really sent, and fix transformation bugs without re-extracting.

---

## 2. Delta Lake: why not plain Parquet?

Parquet files are just files. Delta adds a transaction log (`_delta_log/`, open it in
`data/lakehouse/silver/orders/_delta_log/`) that gives you:

- **ACID writes**: a job that dies halfway leaves no half-written table.
- **MERGE / UPDATE / DELETE** on files in a data lake.
- **Time travel**: `spark.read.format("delta").option("versionAsOf", 3).load(path)`.
- **Schema enforcement and evolution**: bad columns are rejected; new ones can be added with
  `mergeSchema`.

> **Q: What is in the `_delta_log` folder?**
> One JSON file per commit listing the Parquet files added and removed, plus periodic
> checkpoint files. Readers use it to know exactly which files make up the current version.

## 3. Incremental loading with watermarks

Reading 1M rows every day when 500 changed is wasteful. Every source table has an
`_updated_at` column (a Postgres trigger keeps it current, see
`docker/postgres-init/02_load_olist.sql`). Bronze asks only for rows where
`_updated_at > last_watermark`, then saves the new maximum.

Code: `lakehouse/watermark.py`, `extract_query()` in `jobs/bronze.py`.

> **Q: What happens if the job fails after writing but before saving the watermark?**
> Next run re-reads the same rows and appends them to bronze again. That's fine: silver
> de-duplicates and MERGEs, so the final data is still correct. Saving the watermark *after* the
> write is what makes the job safe to retry.
>
> **Q: What's the limitation of watermark-based extraction?**
> It can't see hard deletes (the row is just gone). Real CDC tools like Debezium read the
> database's change log and capture deletes too. That's the next project.

## 4. Idempotency and MERGE

A job is **idempotent** if running it twice gives the same result as running it once. Airflow
retries failed tasks, so every task must be idempotent.

`delta_utils.upsert()` does a Delta `MERGE`: match on the business key, update if it exists,
insert if not. Running it twice with the same input changes nothing the second time. There's a
unit test for exactly that: `test_upsert_is_idempotent`.

> **Q: How do you avoid duplicates when a pipeline is re-run?**
> Upsert on a business key (MERGE) instead of blind appends, and de-duplicate the batch first
> (`dedupe_latest()`), because MERGE fails if two source rows match the same target row.

## 5. De-duplication with window functions

```python
Window.partitionBy("order_id").orderBy(col("_updated_at").desc())
row_number() == 1
```

Groups rows by key, sorts each group newest first, keeps the first. This is one of the most
common interview SQL questions. Practise writing it in SQL too:

```sql
select * from (
  select *, row_number() over (partition by order_id order by _updated_at desc) as rn
  from bronze_orders
) where rn = 1;
```

## 6. Star schema (dimensional modelling)

- **Fact table** = events you measure (items sold): numbers like price, freight, delivery days.
- **Dimension tables** = context you filter and group by (customer, product, seller, date).

The most important decision is the **grain**: what one row of the fact means. Here it's one
item in one order. State the grain first in any modelling interview.

> **Q: Why a date dimension instead of just using the timestamp?**
> It holds precomputed attributes (month name, quarter, weekend flag) and gives a row for every
> day, including days with no sales, which matters for "sales per day" charts.
>
> **Q: What's a surrogate key and why use one?**
> A key generated by the warehouse instead of the source. Here it's a hash of the natural key
> (`xxhash64`), which is deterministic, so the same customer always gets the same key even when
> dimensions and facts are rebuilt separately.
>
> **Q: Slowly Changing Dimensions?**
> This project uses SCD Type 1 (overwrite: a customer who moves just gets the new city). Type 2
> keeps history with `valid_from` / `valid_to` columns. Be ready to explain the difference and
> when you'd need Type 2 (e.g. reporting sales by the region the customer lived in *at the time*).

## 7. Data quality

Two places:

- **Before writing silver** (`lakehouse/quality.py`): not-null keys, unique keys, value ranges,
  allowed values. Error-level failures stop the DAG so bad data never reaches gold.
- **After gold** (dbt tests): referential integrity (every `customer_sk` in the fact exists in
  `dim_customer`), uniqueness, and a reconciliation test that revenue in the mart equals revenue
  in the fact table.

> **Q: How do you make sure your pipeline's numbers are right?**
> Tests at each layer, plus reconciliation: totals at the end must match totals at the start
> (after known filters). Store test results over time so you can see quality trends.

## 8. Spark performance basics used here

- `spark.sql.shuffle.partitions = 8`: the default 200 is meant for big clusters; on small data
  it creates hundreds of tiny tasks and tiny files.
- `.cache()` in bronze/silver: the DataFrame is used several times (count, max, write), so it's
  computed once.
- `OPTIMIZE ... ZORDER BY purchase_date_key` on the fact table: compacts small files and
  co-locates rows with similar dates, so date-filtered queries skip most files.
- Partitioning bronze by `_ingest_date`: reading one day's arrivals touches one folder.

> **Q: What's the small-files problem?**
> Thousands of tiny files make every read slow (each file has overhead to open and plan).
> Fix with fewer shuffle partitions, `OPTIMIZE`/compaction, and sensible partition columns.
>
> **Q: Narrow vs wide transformations?**
> Narrow (filter, select) work within a partition. Wide (groupBy, join, window) need a
> **shuffle**: data moves between executors. Shuffles are the expensive part of most Spark jobs.

## 9. Airflow

- A **DAG** is the pipeline; **tasks** are its steps; `>>` sets the order.
- Each bronze task feeds only its own silver task, so a slow table doesn't block the others.
- `retries=1`: transient failures (network blip) retry automatically. Safe because every task is
  idempotent.
- `max_active_tasks=2`: each task starts its own Spark driver, so this protects your laptop's
  memory.
- `catchup=False`: don't backfill every day since `start_date`.

Code: `dags/olist_lakehouse.py`.

> **Q: What's the difference between the scheduler, the executor and a worker?**
> The scheduler decides what should run; the executor decides how (LocalExecutor here = local
> processes; Celery/Kubernetes executors run tasks on other machines); workers run the tasks.

---

## 10. dbt

dbt turns `SELECT` statements into tables and views, in dependency order (`ref()`), and runs
tests on them. Here DuckDB reads the gold Delta tables directly (`delta_scan`), so analysts get
SQL models without a separate warehouse.

Code: `dbt/olist/models/`, `dbt/olist/tests/`.

> **Q: Why use dbt instead of SQL scripts?**
> Dependency ordering, reusable models, built-in testing, documentation and lineage, and the SQL
> lives in git with code review.

## How to explain this project in 60 seconds

> "I built a batch lakehouse on the Olist e-commerce dataset, about 100 thousand orders across 9
> tables. Postgres acts as the source system. Airflow runs a daily DAG: PySpark extracts only the
> rows that changed since the last run into a bronze Delta layer, cleans and de-duplicates them
> into silver with a MERGE, after data-quality checks, then builds a star schema in gold, with one
> fact table at order-item grain and four dimensions. dbt builds the business marts on top and
> tests referential integrity and revenue reconciliation. Every task is idempotent, so retries are
> safe. CI runs the PySpark unit tests on every push."

## Suggested order to study the code

1. `docker/postgres-init/02_load_olist.sql`: what the source looks like.
2. `lakehouse/jobs/bronze.py` + `watermark.py`: incremental extract.
3. `lakehouse/transforms/silver.py` + `tests/test_silver.py`: cleaning and dedupe.
4. `lakehouse/delta_utils.py` + `quality.py` + `jobs/silver.py`: MERGE and checks.
5. `lakehouse/transforms/gold.py` + `tests/test_gold.py`: star schema.
6. `dags/olist_lakehouse.py`: how it's all scheduled.
7. `dbt/olist/`: marts and tests.

Break something on purpose (e.g. insert a review with score 9 in Postgres) and watch the
pipeline stop at the data-quality check. Being able to describe a failure you caused and fixed is
worth more in an interview than any diagram.
